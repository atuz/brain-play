# 上升牌平台下沿与完成顺序

## 原因和修复

上升牌原先在进入 ceiling 阶段时才补偿平台厚度 18px，同时已开始顶角旋转。因此最终平放位置虽然在平台底部，起转时却仍接近上表面。现在最终一段上升已经包含平台厚度（以及平台抬高量）补偿，转动时不再新增竖直位移，上升采用一致的线性位移。

另一个问题是完成时间含义不一致：普通牌/开门牌在到达接触角时就记下 finish，而它们仍要继续播放至平放；上升牌则到 90° 才记 finish。现在普通牌/开门牌共用 finishFall：碰到下一张仍按原时机触发，完成记录等已有的收尾动画结束才写入。通常收尾 140ms，普通牌落地的接触后收尾为 timing.contact（生产配置 275ms），与各自现有 CSS 相同。完整落地翻转和完整反弹已有单独完成事件，不再重复添加等待。

使用独立 fall-rest 事件，只有对应序号仍有效、牌保持 flat 时才完成，避免把已转入反弹或掉落的牌提前标为完成。通关仍严格比较完成时间，未放宽“机关最后倒下”的条件，也没有把最后被碰到等同于过关。

## 引擎与状态测试

166 项骨牌专项测试及选取的 3 项旧规则/存档/翻译测试通过，共 169 项。新增 8 种左右方向、直接/反弹后撞击、同层/下一层目标的最终机关场景：上升牌完成早于机关，simulate 判定 clear。另有上升过程中即包含平台下沿偏移的视图回归。旧实时钟测试更新为包含实际 140ms 收尾，原接触时间保持不变。静态检查通过（91 个文件），diff 空白检查通过。

专项集合不包括之前已有失败的 domino.test.js 全部旧关卡方案和 domino-actor.test.js 角色夹具；没有声称完整 npm test 通过。

## 真实网页操作

Chrome，localhost:4173 独立存档，HTML 第 64 关。通过公开控件把普通牌放到两张延时牌之间，向左推。旁支会反弹触发右侧延时牌，为隔离左侧上升牌的测量，在连锁过程中公开搬起旁支分叉牌，避免侧撞停止整条模拟。未操作用户 127.0.0.1 存档。

连续读取 DOM 的实际 CSS 矩阵：进入 ceiling 第一帧上升牌约 0°，平台厚度补偿已到 17.55/18px，旋转顶点约在平台下沿下方 0.61px，随后稳定贴下沿，没有从平台上表面穿过板厚再翻转。截图 underside-swing.png。

同次采样相对手推开始：上升牌首次到 90° 为 3660ms，开门牌首次到 90° 为 3711ms，前者约早 51ms。工具采样有帧间隔误差；这不是精确物理计时，结论是视觉顺序与引擎完成顺序一致。采样 browser.json，完成画面 final.png。

本轮网页只验证这段动作，没有验证全关倒完或走出口。引擎 clear 与真实网页通关分开记录。
